## Findings and evidence

| Question | Static observation | Source locations | Implication for SpriteLab |
|---|---|---|---|
| Is an application command the same thing as an undo operation? | No. `Command` has an ID, parameter loading, enabled/checked predicates and an execution hook. `Cmd` separately implements execute/undo/redo and notifications. | `src/app/commands/command.h:23-53`; `src/app/cmd.h:21-44`; `src/app/cmd.cpp:33-76` | Expose stable semantic operations while implementing reversible changes separately. A transport request, command intent and undo patch should not be conflated. |
| Where does application dispatch happen? | The command registry constructs factories and indexes case-insensitive IDs. `Context::executeCommand` loads parameters, emits before/after events, checks enabled state, executes and captures errors. Menu/shortcut dispatch adds a UI-thread/re-entry guard. | `src/app/commands/commands.cpp:26-35,57-71`; `src/app/context.cpp:149-205,224-237` | Build a headless engine with explicit document/target arguments. UI enablement and modal interactions belong in adapters. Aseprite dispatch still depends on Context, active Site and some UI behavior. |
| How are mutations grouped? | `Transaction` executes an initially empty `CmdTransaction`, adds mutations as they execute, commits the sequence to document undo history, and rolls back uncommitted work on destruction. Read-only and undo-in-progress documents reject mutations. | `src/app/transaction.cpp:35-62,83-97,128-162` | A batch can be one atomic, reversible action. Validation should precede mutation where possible; exceptions must roll back earlier successful changes. External files need a separate atomic publication strategy. |
| Does undo reverse order? | `CmdSequence` undoes children in reverse order and redoes them in forward order. Nested notifications can insert more mutations, so children are registered before execution. `Tx` joins a document's current transaction and only its owner commits. | `src/app/cmd_sequence.cpp:31-51,57-70`; `src/app/tx.h:43-69,95-117` | Define deterministic sequencing, nesting and event delivery explicitly. Reentrant callbacks need care: an uncontrolled subscriber can create additional mutations. SpriteLab can publish immutable commit events after its engine finishes. |
| What belongs to history? | `CmdTransaction` captures before/after sprite position and timeline range; document undo supports linear redo clearing and a memory size limit. | `src/app/cmd_transaction.cpp:40-55,78-98,115-134`; `src/app/doc_undo.cpp:43-83` | Separate durable asset state from per-client view state. Track patch memory and prune history deliberately. Capturing GUI selection in an engine history entry should be optional metadata, not a core dependency. |

| Are images the same as cels? | A layer has child layers and cels indexed by frame. A cel has a layer, frame, z-index and a shared `CelDataRef`; CelData owns the image, position and opacity. Linked cels explicitly share CelData. Image holds pixel format/dimensions/row stride. | `src/doc/layer.h:78-80,165-181,210-228`; `src/doc/cel.h:34-60,92-95`; `src/doc/cel_data.h:25-39,93-103`; `src/doc/cel.cpp:58-62`; `src/doc/image.h:31-73` | Model cel identity separately from image storage. Define whether editing a linked cel edits all links or unlinks first. Frame durations are timeline data; a sparse layer need not have a cel at every frame. |
| Where do higher-level edits become reversible mutations? | `DocApi` turns operations such as adding/copying/removing frames, setting duration, inserting/moving layers and setting cels into transaction commands, including tag adjustment. | `src/app/doc_api.cpp:330-393,494-518,663-682,810-843` | A semantic command can expand into several low-level patches while remaining one undo entry. ## Recommended architecture deductions

1. **A shared kernel and command engine, several adapters.** GUI, CLI, Python and MCP accept inputs and invoke the same typed engine request. The engine owns validation, target resolution, transactional mutation, revision checks, undo/redo and commit events. MCP owns protocol handling only.
2. **Separate intent, mutation and rendering.** Public commands such as `raster.stroke`, `layer.insert` and `frame.duplicate` produce reversible mutation groups. Rendering reads document snapshots and optional temporary overlays. UI dialogs choose parameters before submitting a command.
3. **Specify stable identities and explicit targets.** Aseprite's active Site is convenient for interactive use; it is insufficient as a default for concurrent automation. Include document ID, layer/cel/frame IDs, expected revision and request identity in automation envelopes. These are SpriteLab design choices, not behavior established in Aseprite.
4. **Share infrastructure, not a forced universal asset model.** A future 3D module can reuse command registry, transaction coordinator, history contracts, asset catalog and adapter protocols. It should register mesh/material/scene operations and its own patches/renderers rather than representing vertices as cels. Command payloads and document schemas require versioning.
5. **Prove adapter parity through real paths.** Execute the same deterministic operation sequence through GUI submission, CLI batch and MCP; compare canonical document/export hashes and undo round trips. Include failed-batch rollback and stale revision rejection. Source analysis alone does not prove parity, performance, runtime correctness, or release behavior.

All requested source questions are answered at architecture level. Full drawing algorithm coverage, linked-cel mutation behavior, indexed color correctness, shader/CPU pixel parity, file compatibility, crash recovery and performance remain untested or outside this pass.
